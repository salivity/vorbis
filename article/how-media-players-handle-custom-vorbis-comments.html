How Media Players Handle Custom Vorbis Comments

Vorbis comments are the standard metadata container used in audio formats such as Ogg Vorbis, FLAC, and Opus. While the specification encourages flexibility by allowing arbitrary key-value pairs, media players vary significantly in how they process, display, and preserve non-standard custom fields. Depending on the software's architecture, custom Vorbis tags may be fully integrated into a searchable library, relegated to an extended properties window, silently ignored, or, in the worst cases, discarded during file re-tagging.

The Vorbis Comment Structure

Vorbis comments consist of simple UTF-8 text strings formatted as FIELD_NAME=Value. The official specification sets few rigid boundaries; it defines a small set of recommended field names—such as TITLE, ARTIST, and ALBUM—while explicitly allowing users and applications to define any field name composed of printable ASCII characters. Because the format does not use strict binary frames like ID3v2, writing a custom tag requires nothing more than choosing a new field name.

Typical Player Behaviors

Media players generally fall into one of three categories when encountering non-standard Vorbis comments:

  1. Complete Ingestion and Custom Mapping (Power-User Players)
    Advanced desktop media managers—such as foobar2000, MusicBee, and Quod Libet—scan every Vorbis comment in a file regardless of whether it matches a standard specification. These players allow users to create custom database columns, filters, and auto-playlists based on arbitrary keys (such as RELEASETYPE, ORIGINALYEAR, or INSTRUMENT). They expose all non-standard fields directly in their metadata editors and properties dialogues.

  2. Segregated "Extended Info" Display (Standard Players)
    General-purpose players, such as VLC Media Player or Clementine, scan primary tags to build their internal databases and playback displays. When an unrecognized custom tag is encountered, they ignore it for search indexing and playlist views. However, if the user opens the file information or properties panel, the player will often list the custom key-value pairs under an "Extra Metadata" or "Comments" section.

  3. Silent Omission (Minimalist and Mobile Players)
    Mainstream, embedded, and mobile audio players (such as default Android or iOS music apps, streaming-focused software, and automotive infotainment systems) employ rigid database schemas. These systems look strictly for common tags like ARTIST, ALBUM, and TRACKNUMBER. Any non-standard comment is discarded during the library indexing process to reduce memory footprint and maintain UI simplicity. The data remains in the audio file, but the player acts as if it does not exist.

Multi-Value Handling and Case Sensitivity

The Vorbis comment specification states that field names are case-insensitive (MY_TAG is equivalent to my_tag) and permits the same field to appear multiple times to represent arrays of data (e.g., multiple GENRE or PERFORMER fields). Media players handle this differently:

  • Merging: Robust players concatenate duplicate tags using a separator (such as a semicolon or slash) or treat them as native lists.
  • First-Value Truncation: Less flexible players read only the first instance of a tag and drop any subsequent entries with the same key.
  • Case Conflict: Some poorly implemented parsers treat differing cases as distinct keys, which can lead to UI bugs or redundant entries.

Preservation During Tag Modification

A critical distinction among media players is whether they preserve non-standard tags when saving changes. Standard-compliant software reads the entire comment block into memory, modifies only the edited tags, and writes the full block back to disk, keeping custom fields intact. However, substandard audio players or poorly designed tag editors may overwrite the entire comment structure with a hardcoded template of standard tags, unintentionally deleting all custom metadata.
