How Matroska Identifies Vorbis Audio Tracks

This article provides a technical overview of how the Matroska container format (MKV/MKA) recognizes and initializes Vorbis audio streams. Within its Extensible Binary Meta Language (EBML) structure, Matroska relies on specific track header elements—primarily the CodecID string and the binary data stored in the CodecPrivate element—to signal the presence of Vorbis audio and deliver the initialization packets required by decoders.

The TrackEntry Element

In Matroska, every media stream is defined within a TrackEntry master element located inside the container's Tracks element. To identify a stream as audio, Matroska sets the TrackType EBML element (ID 0x83) to a value of 2, which explicitly designates the stream as an audio track.

Identification via CodecID

Matroska does not rely on four-character codes (FourCC) for native audio streams. Instead, it identifies the compression format using the CodecID element (ID 0x86). For Vorbis audio streams, the CodecID string is strictly defined as:

A_VORBIS

When a demuxer parses the TrackEntry and encounters A_VORBIS, it flags the track as Vorbis-encoded audio and prepares the decoding pipeline accordingly.

Initialization Data via CodecPrivate

Vorbis differs from many other audio formats because an audio stream cannot be decoded without three specific header packets:

  1. Identification Header: Contains stream properties such as sample rate, channel count, and Vorbis version.
  2. Comment Header: Contains user metadata and tags (Vorbis comments).
  3. Setup Header: Contains codebooks and decoding configurations necessary to parse the audio blocks.

Because Matroska stores only the raw Vorbis audio frames inside its data clusters (omitting native Ogg container page framing), all three initialization headers must be embedded directly inside the CodecPrivate element (ID 0x63A2) of the track header.

Header Lacing in CodecPrivate

To store all three Vorbis header packets sequentially inside a single CodecPrivate binary field, Matroska uses a specialized header lacing format:

  1. Packet Count Byte: The first byte indicates the number of packets minus one. For Vorbis, this value is almost always 0x02, indicating three packets.
  2. Size of the First Packet: The length of the Identification Header, encoded using byte-based accumulation (bytes of 255 added together until a byte less than 255 appears).
  3. Size of the Second Packet: The length of the Comment Header, encoded using the same accumulation method.
  4. Packet Payloads: The raw payload of the first packet, followed immediately by the second packet, and finally the third packet (the Setup Header). The size of the third packet is not explicitly encoded; the demuxer calculates it by subtracting the first two packet lengths and the lacing overhead from the total size of the CodecPrivate buffer.

Supplemental Audio Header Elements

While the Vorbis identification header inside CodecPrivate contains standard stream parameters, Matroska also duplicates basic audio characteristics inside the track header's Audio master element (ID 0xE1):

  • SamplingFrequency (ID 0xB5): Expressed as a floating-point number matching the sample rate defined in the Vorbis identification header.
  • Channels (ID 0x9F): An integer specifying the channel count (e.g., 2 for stereo, 6 for 5.1 surround).

Demuxers read these parameters to configure output audio devices and pipeline buffers before fully initializing the underlying Vorbis decoder with the payloads retrieved from the CodecPrivate element.
