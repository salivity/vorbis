Vorbis vs PCM RAM Overhead in Game Audio

This article examines the dynamic and static RAM overhead differences between decoding Ogg Vorbis and playing uncompressed PCM audio in video games. It breaks down the memory footprint of both formats across raw asset storage, runtime decoder allocations, and streaming buffer requirements to help developers optimize audio architectures.

Static Storage RAM: Storing Assets in Memory

When an audio file is loaded completely into memory without streaming, uncompressed PCM imposes a massive RAM footprint compared to Vorbis.

Standard uncompressed 16-bit, 44.1 kHz stereo PCM audio requires:

  • 44,100 samples/sec × 2 channels × 2 bytes/sample = 176.4 KB per second (roughly 10.58 MB per minute).

Vorbis uses lossy compression, typically targeting bitrates between 96 kbps and 160 kbps for game audio:

  • At 128 kbps, Vorbis consumes 16 KB per second (roughly 0.96 MB per minute).

If an audio clip is kept in memory in its native format, Vorbis achieves roughly a 10:1 reduction in static RAM consumption over PCM.

Runtime Decoder State and Workspace RAM

While Vorbis drastically lowers storage memory, it introduces dynamic RAM overhead required for the decompression algorithm. PCM requires virtually zero decoding logic or state.

  • PCM Overhead: 0 KB. The audio engine reads PCM samples directly from memory or disk into the audio mixer with no intermediate state.
  • Vorbis Overhead: 10 KB to 100 KB per active voice. The exact memory footprint depends on the decoder implementation:
    • Lightweight decoders like stb_vorbis require roughly 15 KB to 30 KB of setup and working memory per simultaneous stream.
    • Standard reference decoders (libvorbis / Xiph) can consume 50 KB to 100 KB or more per stream to store codebook structures, floor data, residue configurations, and windowing buffers.

Playing 32 simultaneous voices decoded on-the-fly from Vorbis can introduce between 500 KB and 3 MB of pure decoder state overhead in RAM that PCM does not incur.

Streaming Buffer Requirements

For long-form audio such as background music and ambient loops, games rarely hold entire uncompressed tracks in memory. Instead, audio engines stream data in small chunks.

  • Streamed PCM: Requires a simple double-buffer for disk I/O. A typical configuration (two 100 ms buffers at 44.1 kHz/16-bit stereo) requires about 35 KB of RAM per channel.
  • Streamed Vorbis: Requires an input buffer for compressed data chunks (8 KB to 16 KB), the decoder workspace allocation (15 KB to 50 KB), and an output PCM staging buffer (16 KB to 32 KB) to feed the mixer. Total streaming RAM overhead ranges between 40 KB and 100 KB per active stream.

Even with the decoder workspace included, streaming Vorbis from disk saves vast amounts of memory compared to loading a full PCM file, while using only slightly more working RAM than streaming raw PCM.

The Deciding Threshold: Short SFX vs. Music

The RAM efficiency between the two formats depends on the duration and concurrency of the sound:

  • Short Sound Effects (< 2–3 seconds): Pre-decompressing to PCM or keeping the source as uncompressed PCM is often more RAM-efficient than decoding Vorbis in real-time. A 0.5-second UI click takes only 88 KB as raw PCM. Decoding that same sound from Vorbis requires storing the compressed file (around 8 KB) plus allocating 15 KB to 50 KB for the decoder state during playback. When accounting for CPU overhead and decoder allocations, Vorbis provides little to no RAM advantage for ultra-short clips.
  • Long Audio (> 10–15 seconds): Vorbis is significantly more memory-efficient. A 2-minute music track in uncompressed PCM requires over 21 MB of RAM. Using a streamed Vorbis implementation reduces the footprint to under 100 KB of working RAM, freeing tens of megabytes of system memory.
