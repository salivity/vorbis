Parsing Multiple ARTIST Vorbis Tags

This article explains how software music players handle multiple occurrences of the ARTIST= Vorbis comment within digital audio files such as FLAC, Ogg Vorbis, and Opus. While the underlying specification explicitly supports repeated field names to represent distinct entries, media players differ significantly in how they parse, store, and display this data. Below is a breakdown of the standard mechanisms players use, ranging from native multi-value support and string concatenation to destructive key-value overwrites.

The Vorbis Comment Standard

The Vorbis comment specification natively supports repeated field names. Unlike metadata containers that require all values to reside in a single delimited string, a Vorbis comment block can contain separate, identical field names:

ARTIST=Alice
ARTIST=Bob

According to Xiph.Org, field names are not required to be unique, and repeated fields are the intended method for handling multiple attributes of the same type. Despite this standard, downstream software music players parse this structure using one of three primary approaches.

1. Native Array Storage (Multi-Value Support)

Modern, library-focused music players—such as MusicBee, Foobar2000, and Quod Libet—follow the official specification.

  • Internal Parsing: The parser reads the tag stream sequentially. When it encounters multiple ARTIST= fields, it appends each value into a list or array associated with the track object (e.g., artists: ["Alice", "Bob"]).
  • Library Indexing: The database engine indexes the file under both entries independently. A search or filter for "Alice" returns the track, and a search for "Bob" returns the exact same track.
  • Display Rendering: In the user interface, the player temporarily joins the array elements using a user-configurable visual separator (commonly a comma, semicolon, or slash) without modifying the underlying raw metadata.

2. In-Memory String Concatenation

Some media engines read all instances of the tag but do not store them as discrete array items in their internal database.

  • Internal Parsing: During the initial file scan, the parser detects repeated ARTIST= keys and merges them into a single string using a fixed hardcoded delimiter (such as ; , /, or &).
  • Library Indexing: The database treats the concatenated string as a single artist name (e.g., Alice; Bob). Unless the player includes specific logic to split fields on that delimiter during queries, the software will not categorize the track under "Alice" or "Bob" individually.
  • Display Rendering: The user sees the merged string directly, which can cause inconsistent formatting if different files use different metadata styles.

3. Key-Value Overwriting (Dictionary Collision)

Simpler, legacy, or mobile audio players often parse metadata into a basic key-value map (such as a standard hash table or dictionary) where keys must be unique.

  • Last-Write Wins: As the parser iterates through the metadata, each subsequent ARTIST= tag overwrites the previous entry stored at the ARTIST key. In a file containing ARTIST=Alice followed by ARTIST=Bob, the player only retains Bob.
  • First-Write Wins: Alternatively, some parsers check if the key already exists and ignore any subsequent duplicates, discarding Bob and retaining only Alice.
  • Result: The track is only indexed and displayed under one contributor, causing incomplete library searches and incorrect display metadata.

External Services and Scrobbling Complications

Parsing behavior directly impacts external integrations like Last.fm scrobbling and streaming server syncing (such as Subsonic or Plex). Most external APIs expect a single artist string per track. As a result, even players with native array handling must flatten multiple ARTIST= tags into a single string prior to transmitting data, often selecting the first encountered tag or joining them with a forward slash.
