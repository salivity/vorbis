How OggS Capture Pattern Locates Vorbis Packets

The OggS capture pattern functions as the primary synchronization anchor in an Ogg container, enabling demuxers to locate page boundaries within a continuous byte stream. By identifying this four-byte sequence, an Ogg parser can read the subsequent header metadata, interpret the page segment table, and reassemble raw byte chunks into complete, discrete Vorbis audio packets ready for decoding.

Stream Synchronization via the Capture Pattern

An Ogg bitstream is structured as a sequence of discrete units called pages. When reading an arbitrary or fragmented stream—such as during seeking or recovering from transmission loss—the demuxer scans the byte stream sequentially until it identifies the four-byte ASCII sequence OggS (0x4F 0x67 0x67 0x53).

This capture pattern marks the absolute start of an Ogg page header. Once detected, the parser treats the subsequent bytes as structured header fields rather than arbitrary payload data.

Reading the Ogg Page Header

Immediately following the OggS capture pattern, the demuxer reads the 23-byte fixed header to validate and identify the page:

  1. Stream Structure Version (1 byte): Typically set to 0x00.
  2. Header Type Flag (1 byte): Indicates page properties, such as continuation of an earlier packet, beginning of stream (BOS), or end of stream (EOS).
  3. Granule Position (8 bytes): Specifies the time/sample position of the stream for seeking and timing.
  4. Bitstream Serial Number (4 bytes): Distinguishes between different multiplexed logical streams (for example, separating a Vorbis audio track from a Theora video track).
  5. Page Sequence Number (4 bytes): Ensures pages are processed in sequential order.
  6. CRC32 Checksum (4 bytes): Validates page integrity. If the checksum fails, the parser discards the block and scans forward for the next OggS sequence.
  7. Page Segments Count (1 byte): Dictates how many lacing values follow in the segment table.

Demuxing Packets with the Segment Table

Vorbis codec packets do not have fixed boundaries directly stamped in the page payload; instead, their boundaries are defined by the Ogg lacing mechanism.

Following the fixed 27-byte header is the segment table, which contains between 1 and 255 single-byte values (lacing values). Each lacing value represents the length of a data segment in bytes, ranging from 0 to 255:

  • Packet Termination: Any segment with a length strictly less than 255 bytes marks the end of a Vorbis packet.
  • Packet Continuation: A segment length of exactly 255 bytes indicates that the current Vorbis packet spans across segment boundaries. The parser appends the next segment's data directly to the current packet.
  • Large Packets: If a Vorbis packet is 600 bytes long, its segment representation will consist of 255, 255, and 90. The third value (90 < 255) indicates that the packet terminates after these 90 bytes.
  • Multi-Page Spanning: If a packet exceeds the remaining capacity of a page, the page ends on a 255 lacing value, and the continued packet flag is set on the subsequent page following the next OggS capture pattern.

Delivering Data to the Vorbis Decoder

Once the segment table is fully parsed, the demuxer slices the page payload into distinct Vorbis packets based on the accumulated lacing lengths. By filtering these extracted packets using the page’s Bitstream Serial Number, the demuxer isolates the Vorbis logical stream and forwards the reconstructed byte arrays—beginning with the initial identification, comment, and setup headers, followed by raw audio packets—directly to the Vorbis audio decoder.
