Vorbis Codebook Binary Representation

This article provides an overview of the binary representation of a Huffman-encoded Vorbis codebook, detailing how the Vorbis audio codec serializes vector quantization dictionaries and prefix-free trees. It covers the exact bitstream layout defined in the Vorbis specification, including the synchronization header, codebook dimensions, codeword length packing strategies, canonical Huffman tree construction, and the associated vector value lookup tables.

Header Fields

A Vorbis codebook begins with identification and dimension metadata written directly to the bitstream in little-endian bit order:

  • Sync Pattern (24 bits): The static byte sequence 0x56, 0x43, 0x42 (ASCII "BCV" for Book Code Vorbis).
  • Dimensions (16 bits): An unsigned integer defining the vector dimensionality of each codebook entry (1 to 65,535).
  • Entries (24 bits): An unsigned integer defining the total number of entries in the codebook (up to 16,777,215).

Codeword Length Assignment (Huffman Tree Definition)

Vorbis does not transmit the Huffman tree nodes directly. Instead, it transmits the bit length of each entry's codeword. Because Vorbis uses canonical Huffman codes, a decoder reconstructs the exact prefix-free tree purely from this ordered list of lengths.

The binary format encodes lengths using one of two primary strategies indicated by a single flag bit:

1. Ordered Representation (ordered_flag = 1)

When codeword lengths are sorted in non-decreasing order, Vorbis uses run-length encoding:

  • Current Length (5 bits): The initial codeword length minus one (representing lengths 1 to 32).
  • Run Length: For each length step, the bitstream stores the count of entries sharing this length using ceil(log2(remaining_entries)) bits. The length increments by one for each subsequent run until all entries are accounted for.

2. Unordered Representation (ordered_flag = 0)

When lengths are not sorted, Vorbis evaluates whether the codebook is sparse:

  • Sparse Flag (1 bit):
    • If 0 (dense): Every entry exists. The bitstream reads 5 bits per entry sequentially to denote each codeword's length (encoded as length minus one). A length value of zero indicates an unused entry.
    • If 1 (sparse): Entries may be omitted. Each entry begins with a 1-bit presence flag. If 1, it is followed by 5 bits specifying the codeword length. If 0, the entry is skipped and assigned an unused status.

Reconstructing the Canonical Huffman Codes

Once all entry lengths are parsed, the decoder assigns binary codewords using canonical construction rules:

  1. Entry lengths of zero are discarded.
  2. The remaining entries are sorted primarily by bit length, maintaining their original index order as a secondary key.
  3. The first entry receives a codeword of all zeros with a length equal to its assigned length.
  4. Each subsequent entry increments the integer value of the preceding codeword by one, then left-shifts the result if the current entry's length is greater than the previous entry's length.
  5. In the bitstream, these Huffman codewords are read least-significant bit (LSB) first.

Vector Lookup Tables

Following the codeword definitions, the bitstream specifies how vector scalar values are mapped to each codeword:

  • Lookup Type (4 bits):
    • 0: No lookup table (the codebook index itself is the output, or values are unused).
    • 1: Implicitly generated lattice-based vector quantization table.
    • 2: Explicitly stored multidimensional vector quantization table.

If the lookup type is 1 or 2, the stream unpacks the following quantization parameters:

  • Minimum Value (32 bits): Stored as a custom low-precision IEEE 754-like float.
  • Delta / Step Size (32 bits): Stored as the same 32-bit float format, indicating the step size between quantization levels.
  • Value Bits (4 bits): The bit depth minus one used to unpack each quantization multiplier.
  • Sequence Flag (1 bit): Indicates whether values in a vector are absolute or sequential deltas.
  • Multipliers List: A sequence of values unpacked using value_bits + 1 bits each. For lookup type 1, it reads floor(entries^(1/dimensions)) multipliers; for lookup type 2, it reads entries * dimensions multipliers.
