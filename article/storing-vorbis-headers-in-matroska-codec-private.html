Storing Vorbis Headers in Matroska CodecPrivate

This article details how the three essential Vorbis header packets—Identification, Comment, and Setup—are encapsulated within the Matroska CodecPrivate element. Because Matroska stores these initialization packets as a single contiguous binary block rather than individual stream packets, it employs a specific multiplexing structure known as Xiph-style lacing. Understanding this format is necessary for demuxing Matroska streams containing A_VORBIS audio and correctly initializing a Vorbis decoder.

The Vorbis Initialization Requirement

The Vorbis audio specification mandates three distinct header packets at the start of a stream, delivered in strict sequential order:

  1. Identification Header: Contains stream parameters like sample rate, channels, and bitrates.
  2. Comment Header: Contains human-readable metadata (Vorbis comments).
  3. Setup Header: Contains complex codebook, floor, and residue configurations required to decode the audio packets.

In Ogg containers, these exist as individual sequential packets. In Matroska, all three are combined into a single byte array located inside the track's CodecPrivate element (0x63A2).

The Binary Layout of CodecPrivate

Matroska uses an initial count byte followed by Xiph-style lacing to indicate packet boundaries, succeeded immediately by the concatenated packet payloads. The complete payload inside CodecPrivate is laid out as follows:

  1. Packet Count Indicator (1 byte): Represents the total number of packets minus one (\(N - 1\)). For Vorbis, which always uses three headers, this value is 0x02 (\(3 - 1 = 2\)).

  2. Packet Sizes (Xiph Lacing): The sizes of the first \(N - 1\) packets (the Identification and Comment headers) are encoded consecutively using Xiph lacing. The size of the final packet (the Setup header) is omitted because it is derived mathematically.

    • Xiph Lacing Mechanism: A size is encoded as a sequence of 0xFF (255) bytes, terminated by a byte less than 0xFF. The total packet size is the sum of these bytes. For example:
      • A size of 30 bytes is encoded as 0x1E.
      • A size of 512 bytes is encoded as 0xFF, 0xFF, 0x02 (\(255 + 255 + 2 = 512\)).
    • First, the size of Packet 1 (Identification) is written using Xiph lacing.
    • Immediately following, the size of Packet 2 (Comment) is written using Xiph lacing.

  3. Implicit Final Packet Size: The size of Packet 3 (Setup) is calculated by taking the total length of the CodecPrivate buffer and subtracting the byte length of the packaging overhead (count byte + lacing bytes) along with the computed lengths of Packet 1 and Packet 2.

  4. Concatenated Header Data: Immediately following the last lacing byte, the raw data for all three packets is stored contiguously:

    • Identification Header Data
    • Comment Header Data
    • Setup Header Data

Demuxing Procedure

To extract and pass these headers to a Vorbis decoder (such as libvorbis via vorbis_synthesis_headerin), a parser executes the following steps:

  1. Read the first byte of CodecPrivate to confirm the packet count equals 2.
  2. Decode the Xiph-laced size of the first packet (\(L_1\)).
  3. Decode the Xiph-laced size of the second packet (\(L_2\)).
  4. Note the offset in the buffer where lacing ends (\(O_{data}\)).
  5. Compute the size of the third packet: \(L_3 = \text{TotalBufferLength} - O_{data} - L_1 - L_2\).
  6. Slice the buffer:
    • Identification: Bytes from \(O_{data}\) to \(O_{data} + L_1\)
    • Comment: Bytes from \(O_{data} + L_1\) to \(O_{data} + L_1 + L_2\)
    • Setup: Bytes from \(O_{data} + L_1 + L_2\) to the end of the buffer.

Once extracted, these three distinct byte buffers can be fed directly to the Vorbis initialization routines in their original order.
